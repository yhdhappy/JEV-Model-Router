# JEV Model Router — 项目定位说明

版本：v1.0
生成方式：项目顾问澄清对话整理

---

## 一句话描述

JEV Model Router 是一个面向"不懂技术、靠 Agent 做开发"的个体开发者的 AI 模型智能路由工具——自己先用起来，未来开源到 GitHub，通过 JEV 判断任务难度自动分配合适模型，在保证任务质量的前提下把 AI 调用成本降下来。

---

## 六个维度的结论

### 1. 目标（做成什么）
自己用的同时，把它在 GitHub 上公开，让别人也能用、也能一起完善。
不是一开始就做成商业产品，也不是纯技术练手项目。

### 2. 为什么做（动机）
作为不懂开发的普通人，靠 Agent 完成开发任务，但分不清该用哪个模型——不同模型价格差异很大，成本因此偏高。希望 JEV 能替自己做这个判断，从而控制成本。

### 3. 给谁用（目标用户）
像自己一样的非技术背景个体开发者/创业者：用 Agent（Codex、DeepSeek Harness、PI Agent 等）做开发，但不懂如何选模型。

### 4. 什么样算成功
自己实际使用一段时间后，明显感受到 AI 调用成本下降，且任务完成质量没有变差。

### 5. 资源与约束
完全依靠 Codex、DeepSeek Harness、PI Agent 写代码，自己不会写代码；**连任务拆解本身也不懂，需要 Agent 来完成**。这是本项目区别于普通开发项目的关键约束。

### 6. 时间线
不赶时间，先把最小可行的一条链路（任务 → JEV → Router → 模型 → 结果）跑通，不设固定日期。

---

## 3 个关键判断

1. **定位是"自用优先、顺带开源"，不是商业产品。**
   第一版不需要考虑收费、运营、获客，只需要对自己好用。

2. **核心诉求是控制成本，不是追求最强效果。**
   目标用户（包括你自己）看不懂技术细节、甚至连任务拆解都要靠 Agent 完成——这意味着产品的 UI 和使用方式必须做到极致"傻瓜化"，不能假设用户会配置 YAML。

3. **节奏上不设死期，先验证最小链路能不能跑通。**
   成功的标准很朴素：自己实际用一段时间，明显感觉省钱了，活儿的质量没打折扣。

## 对原产品方案（v0.1）的启发

以下是基于上述结论，原方案（`JEV_Model_Router_产品方案_v0.1.md`）中值得注意的几点，供后续讨论：

- **"开发者直接编辑 YAML" 这条路径应定位为次要路径，而非主路径。** 原方案第十节把"普通用户"和"开发者"并列展开，但结合目标用户画像（不懂技术），UI 化的自动路由应该是唯一必须打磨好的路径，配置文件路径可以先不实现或简化。
- **"分层路由""路由学习机制建议"等进阶功能（原方案第八、十五节）可以放到最小链路跑通之后再做**，第一版不必追求这些优化能力，避免任务拆解难度过大。
- **既然任务拆解也要靠 Agent 完成，方案文档本身需要写得比一般产品文档更"啰嗦、具体"**，每个功能点最好能直接转成一条可以喂给 Codex/DSH 的独立任务，减少你自己居中判断的负担。
