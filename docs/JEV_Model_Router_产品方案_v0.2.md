## 0. v0.2 相比 v0.1 的主要变化

v0.2 不推翻 v0.1 的核心架构，而是重新收紧产品定位和第一阶段开发范围。

主要变化：

1. 明确产品定位为：**自用优先、未来开源，不以第一版商业化为目标。**
2. 明确第一目标用户为：**不懂开发、依靠 Agent 完成开发任务的个人开发者/创业者。**
3. UI 成为普通用户的主路径；配置文件降为开发者高级路径。
4. “路由学习机制”移出 MVP，保留为后续能力。
5. “分层路由”保留在架构设计中，但不作为第一阶段必须实现的功能。
6. 新增最关键的产品验证：**先证明 JEV 的判断能够带来真实成本收益。**
7. 明确 JEV、Router 自身产生的调用成本必须计入总成本，不能只计算最终执行模型成本。
8. 将“感觉省钱”升级为可测量的验证指标。
9. 第一阶段开发目标从“完整路由产品”收缩为：**先跑通并验证最小闭环。**

# 一、产品一句话定位

**JEV Model Router 是一个面向“不懂技术、主要依靠 Agent 做开发”的个人用户的 AI 模型智能路由工具：在真正调用执行模型之前，通过轻量规则和 JEV 判断任务类型与难度，再结合模型能力和成本自动选择合适模型，在任务质量不明显下降的前提下降低 AI 调用总成本。**

第一阶段首先服务自己。

当实际使用证明有效后，再开源到 GitHub，让其他人使用、测试和完善。

# 二、为什么要做这个产品

## 2.1 当前问题

使用 Codex、DeepSeek Harness、PI Agent 等 Agent 做开发时，经常会同时拥有多个不同能力和价格的模型。

例如：

- 一个便宜、速度快、能力较弱的模型；
- 一个中档模型；
- 一个价格较高、能力更强的模型。

真正的问题不是“有没有模型”，而是：

> **普通用户不知道当前任务到底需要哪个级别的模型。**

如果所有任务都使用最强模型：

- 成本很高；
- 很多简单任务浪费高级模型额度；
- 用户需要不断手动判断和切换模型。

如果为了省钱总使用便宜模型：

- 复杂任务可能失败；
- 容易返工；
- 最终总体成本反而更高。

对于不会开发的用户，这个问题更明显，因为用户甚至无法准确判断：

- 这个任务到底难不难；
- 当前是代码修改、架构设计还是调试；
- 是否需要高推理模型；
- 失败究竟是模型不够强，还是任务本身有问题。

因此希望由 Router 帮用户完成这个判断。

# 三、目标用户

## 3.1 第一目标用户

第一目标用户不是专业程序员，而是：

**不懂开发或开发能力较弱，但依赖 AI Agent 完成开发工作的个人开发者、创业者和 AI 工具重度用户。**

典型特征：

- 使用 Codex、DeepSeek Harness、PI Agent 等 Agent；
- 自己不会或不擅长写代码；
- 连开发任务拆解也经常依赖 Agent；
- 同时拥有多个模型或多个模型套餐；
- 不知道什么时候应该使用便宜模型、什么时候需要强模型；
- 希望控制调用成本，但不希望因为省钱导致任务质量明显下降。

## 3.2 第二目标用户

未来开源后，也允许有开发能力的用户使用。

这部分用户可能更关心：

- YAML / JSON 配置；
- 自定义 Router 策略；
- 自定义 Provider；
- 自定义模型能力标签；
- 自定义 Adapter；
- 二次开发。

但这不是 v0.1 / v0.2 MVP 的首要设计对象。

---

# 四、产品目标

JEV Model Router 的目标不是“永远选择最强模型”。

也不是“永远选择最便宜模型”。

核心目标是：

> **先保证任务有较高概率完成，再在满足能力要求的候选模型中尽可能降低总成本。**

三个核心判断因素确定为：

1. **任务类型**
2. **任务难度**
3. **成本**

“速度”暂时不作为一级路由因素。

以后如果实测发现速度非常重要，可以再增加。

---

# 五、非目标

第一阶段明确不做以下事情：

1. 不做商业化收费系统。
2. 不做用户增长、账号体系、运营后台。
3. 不同时支持十几个 Agent 平台。
4. 不一开始就做复杂的自动学习系统。
5. 不允许 Router 未经用户批准自动修改正式生产路由规则。
6. 不要求普通用户学习 YAML、JSON、环境变量等开发知识。
7. 不追求“一次开发完成所有高级功能”。

第一阶段只证明一件事：

> **JEV + Router 这套机制，是否真的能在保持任务质量的情况下省钱。**

# 六、产品最重要的两个假设

整个项目是否值得继续，取决于两个核心假设。

## 6.1 假设一：JEV 能够稳定判断任务

JEV 至少需要对以下信息给出足够稳定的判断：

- 任务类型；
- 难度；
- 所需能力级别；
- 判断置信度。

如果 JEV 经常把：

```text
简单任务 → 判断成困难任务
```

则 Router 会过度调用高级模型，成本无法降低。

如果 JEV 经常把：

```text
困难任务 → 判断成简单任务
```

则任务失败和返工会增加。

因此：

**JEV 判断准确性不是一个附加指标，而是整个产品成立的前提。**

## 6.2 假设二：路由产生的节省必须大于路由自身成本

Router 不是免费的。

每一次：

```text
任务 → JEV → Router → 执行模型
```

都可能增加：

- JEV Token 成本；
- 网络请求成本；
- 时间成本；
- 失败重试成本。

因此不能只计算最终执行模型费用。

必须计算：

```text
任务总成本
=
轻量判断成本
+ JEV 判断成本
+ Router 额外调用成本
+ 执行模型成本
+ fallback 成本
+ 返工成本
```

只有最终总成本真正下降，产品才算成功。

# 七、产品成功标准

不再使用“感觉省钱了”作为唯一判断标准。

正式成功标准应建立在一组真实任务的 A/B 基准测试上。

## 7.1 最低验证指标

测试中至少记录：

- 总任务数；
- 每个任务类型；
- JEV 判断结果；
- Router 选择模型；
- 执行成功/失败；
- 是否返工；
- 最终总成本；
- JEV / Router 额外成本；
- 与固定模型策略相比的成本变化；
- 与固定模型策略相比的成功率变化。

## 7.2 成功原则

满足：

> **总模型成本明显下降，任务成功率没有明显下降，返工率没有明显上升。**

具体“下降多少百分比算成功”暂时不拍脑袋设定。

先完成第一轮基准测试，再确定正式目标，例如：

```text
总成本下降 ≥ X%
任务成功率下降 ≤ Y%
返工率增加 ≤ Z%
```

X、Y、Z 由真实测试数据决定。

# 八、总体工作流程

第一阶段工作流程：

```text
用户提交任务
        ↓
是否手动指定模型？
   ┌────┴────┐
   是        否
   ↓          ↓
指定模型    轻量规则判断
               ↓
        能否非常明确判断？
          ┌────┴────┐
          是        否
          ↓          ↓
       Router      JEV
                     ↓
              结构化判断结果
                     ↓
                  Router
                     ↓
          任务类型 + 难度
                     ↓
            候选模型集合
                     ↓
               成本策略
                     ↓
            主模型 / 备用模型
                     ↓
                 执行任务
                     ↓
              记录实际结果
```

MVP 到这里结束。

第一阶段不要求 Router 自动学习和修改策略。

# 九、为什么必须有“轻量规则层”

不能让所有任务都调用 JEV。

例如：

- 改一个文件名；
- 读取一个文件；
- 修改一行文字；
- 翻译一句短文本；
- 执行明确的机械操作。

这些任务如果每一次都先调用 JEV：

```text
原始任务成本：1

加入 JEV：
JEV 判断：0.2
执行模型：1

总成本：1.2
```

Router 反而增加成本。

因此采用两级机制：

## 第一层：轻量规则

只识别非常确定的低风险场景。

原则：

> **宁可少拦截，也不要错误判断复杂任务。**

## 第二层：JEV

只有轻量规则无法明确判断时，才调用 JEV。

这样 JEV 负责真正需要语义理解的任务，而不是成为所有请求的固定税费。

# 十、JEV 的职责

JEV 的职责不是决定最终模型名称。

JEV 只负责对任务进行结构化理解。

示例输出：

```json
{
  "task_type": "coding",
  "difficulty": 7,
  "required_capability": "high",
  "cost_sensitivity": "medium",
  "context_size": "medium",
  "confidence": 0.91
}
```

其中至少包含：

- task_type
- difficulty
- required_capability
- confidence

可选字段：

- context_size
- cost_sensitivity
- risk_level
- notes

---

# 十一、为什么 JEV 不直接输出模型名

不设计成：

```text
JEV → GPT 6 Sol
```

而设计成：

```text
JEV
↓
任务属性
↓
Router
↓
模型
```

原因：

模型会不断变化。

以后可能：

- 模型改名；
- 模型价格改变；
- 某模型取消；
- 新增 DeepSeek；
- 新增 Claude；
- 新增 Qwen；
- 新增本地模型。

如果 JEV 直接输出模型名，每次模型变化都可能需要调整分类提示词。

正确做法是：

> **JEV 负责理解任务，Router 负责理解模型。**

---

# 十二、Router 的模型选择逻辑

Router 采用三个主因素：

## 12.1 任务类型

例如：

```text
coding
debugging
architecture
research
writing
translation
review
testing
reasoning
data-analysis
```

任务类型首先用于排除明显不适合的模型。

## 12.2 难度

暂定 1～10：

```text
1–3   简单
4–6   中等
7–8   困难
9–10  极难
```

难度本身不直接绑定模型名称。

## 12.3 成本

在满足能力要求的候选模型中，再比较成本。

原则：

> **先满足能力要求，再在满足条件的模型里选更便宜的。**

不是：

> 最便宜模型永远优先。

---

# 十三、模型配置

每个模型至少记录：

```text
模型名称
Provider
能力等级
擅长任务类型
不适合任务类型
输入价格
输出价格
上下文能力
当前是否可用
凭证引用
```

未来可以增加：

- 成功率；
- 平均返工率；
- 平均响应时间；
- 实测 Coding 能力；
- 实测 Review 能力。

这些数据不要求第一版全部自动生成。

---

# 十四、主模型、备用模型和成本上限

每类任务可以配置：

```text
主模型
备用模型 1
备用模型 2
单任务成本上限
```

例如：

```text
任务类型：普通 Coding

主模型：
GPT 6 Sol

备用：
DeepSeek
GPT 6 Astra

单任务最大预算：
$0.50
```

当主模型：

- 不可用；
- 超时；
- 额度不足；
- 调用失败；

才进入备用链。

不能无限升级。

超过预算上限后停止自动升级，并向用户说明原因。

---

# 十五、JEV 故障降级

JEV 不能成为系统单点故障。

基本降级流程：

```text
JEV 正常
→ 正常路由

JEV 超时 / 报错
→ 使用保守规则判断

仍无法判断
→ 使用默认保底模型

保底模型失败
→ 进入备用模型链
```

同时记录：

```text
fallback_reason
```

例如：

```text
fallback_reason: jev_timeout
```

---

# 十六、手动选择模型

Router 必须保留人工控制权。

UI 的模型选择控件默认：

```text
● 自动选择
○ GPT 6 Luna
○ GPT 6 Sol
○ GPT 6 Astra
○ DeepSeek
○ Claude
○ 其他模型
```

默认是：

**自动选择**

代表：

```text
轻量规则 → JEV（必要时）→ Router
```

如果用户手动选择：

```text
GPT 6 Astra
```

此次任务直接使用该模型。

记录：

```text
route_source: manual_override
```

手动选择只覆盖当前任务。

不能偷偷修改全局默认规则。

下一次新任务默认仍回到“自动选择”。

# 十七、UI 是普通用户的主路径

v0.2 明确调整优先级：

**UI 是唯一必须打磨好的普通用户路径。**

普通用户不应该需要理解：

- YAML；
- JSON；
- Provider 配置格式；
- 环境变量；
- 终端命令；
- Router 内部算法。

普通用户应该可以通过 UI 完成：

- 添加模型；
- 选择 Provider；
- 设置 API 凭证；
- 设置模型价格；
- 设置模型能力等级；
- 设置主模型；
- 设置备用模型；
- 设置预算上限；
- 开启自动路由；
- 手动选择模型；
- 查看 Router 为什么选择这个模型；
- 查看本次大概花费；
- 查看 fallback 是否发生。

# 十八、开发者配置路径

配置文件仍然保留，但降为高级能力。

例如：

```text
models.yaml
router.yaml
providers.yaml
privacy.yaml
```

原则：

> 普通用户完全不碰配置文件，也能够正常使用全部核心功能。

开发者可以直接修改配置文件，以便：

- 批量配置；
- 自动部署；
- Git 管理；
- 二次开发；
- 自定义 Provider。

MVP 可以先实现内部配置存储，但不要求第一阶段把“手动编辑 YAML”打磨成完整产品功能。

# 二十、凭证管理

Router 不直接在普通配置文件中保存明文 API Key。

配置中保存：

```text
credential_ref: openai-main
```

底层根据部署环境读取：

- macOS Keychain；
- 环境变量；
- Docker Secret；
- Server Secret Manager；
- 后续其他凭证系统。

UI 对普通用户可以显示：

```text
OpenAI：已连接
JEV：已连接
DeepSeek：未配置
```

而不是直接展示完整密钥。

# 二十四、Skill、插件、Router 的关系

这个项目不定义成单纯 Skill。

正确关系：

```text
                 JEV Router Core
                       ↑
        ┌──────────────┼──────────────┐
        │              │              │
      Codex     DeepSeek Harness    PI Agent
        │              │              │
     Adapter         Adapter         Adapter
        │
     Skill / Plugin
     作为接入方式
```

因此：

**Router 是产品本体。**

**Adapter 是平台连接层。**

**Skill / Plugin 是某些平台上的安装或调用方式。**

# 二十五、分层路由的处理方式

v0.1 方案中的“分层路由”仍然保留。

例如：

```text
开发登录系统
→ Sol

进入架构设计
→ Astra

只是修改按钮文案
→ Luna

进入安全审查
→ Astra
```

这个方向是合理的。

但是：

**不作为第一阶段 MVP 必须实现。**

第一阶段先实现：

```text
一个独立任务
→ 判断一次
→ 选择模型
→ 执行
→ 记录结果
```

架构上不要阻止未来的子任务重新路由能力。

等最小链路验证成功后，再增加：

```text
复杂 Agent 任务
↓
检测任务阶段变化
↓
重新路由
```

# 二十六、Router 学习机制的处理方式

v0.1 中的路由学习机制不删除，但整体后移。

未来系统可以统计：

```text
任务类型
难度
模型
成功率
成本
返工率
fallback 率
```

并生成建议，例如：

```text
过去 100 个 Coding 难度 5–6 的任务：

Sol：
成功率 95%
平均成本 $0.18

Astra：
成功率 96%
平均成本 $0.42

建议：
该任务区间默认模型从 Astra 调整为 Sol。
```

但 Router 只能生成建议。

必须：

```text
生成建议
↓
用户查看
↓
用户批准
↓
策略修改
```

不能自行修改生产策略。

该功能不属于 MVP。

# 二十七、MVP 第一阶段：先验证，不追求完整

第一阶段不是直接开发一个“大而全”的 Router。

第一阶段目标：

> **验证最小链路在真实任务里是否能够降低总成本。**

最小链路：

```text
任务
↓
轻量规则
↓
必要时 JEV
↓
Router
↓
候选模型
↓
执行
↓
记录结果和总成本
```

第一阶段只需要支持少量明确模型。

例如：

```text
低成本模型
中档模型
高能力模型
```

可以映射为当前实际使用的 Luna / Sol / Astra，或者其他真实可用模型。

# 二十八、MVP 基准实验

在正式扩展功能之前，必须做一轮真实任务验证。

## 28.1 测试集

准备约：

**50～100 个真实任务。**

任务来源应尽量来自真实 Agent 开发工作，而不是为了测试人为编造大量简单题。

覆盖：

- 文件操作；
- 小型代码修改；
- 普通 Coding；
- Debug；
- 测试；
- Review；
- 架构分析；
- 长上下文任务；
- 复杂推理。

## 28.2 对照方案

至少比较：

### A. 固定便宜模型

所有任务统一使用低成本模型。

### B. 固定中档模型

所有任务统一使用中档模型。

### C. 固定高能力模型

所有任务统一使用高能力模型。

### D. JEV Router

由 Router 自动选择。

## 28.3 记录指标

每项任务记录：

```text
任务 ID
任务类型
任务难度
JEV 判断
JEV 置信度
Router 选择
最终模型
JEV 成本
模型执行成本
总成本
是否成功
是否返工
返工次数
最终是否完成
```

## 28.4 最终问题

实验只回答三个问题：

1. Router 是否真的省钱？
2. 省钱以后任务质量有没有明显下降？
3. JEV 判断和路由本身的额外成本值不值得？

如果答案不理想：

**优先修改核心判断策略，而不是继续增加功能。**

# 三十五、设计原则

## 原则 1：普通用户优先

不假设用户懂开发。

## 原则 2：先证明省钱

不要因为产品听起来聪明，就默认它有价值。

## 原则 3：总成本，而不是单次模型价格

JEV 自身成本必须计入。

## 原则 4：不牺牲明显质量换成本

失败和返工也是成本。

## 原则 5：路由可解释

至少告诉用户：

```text
为什么选这个模型
```

## 原则 6：最终控制权属于用户

自动模式是默认。

手动覆盖始终存在。

## 原则 7：核心与平台解耦

Router Core 不绑定 Codex、DeepSeek Harness 或 PI Agent。

## 原则 8：模型可替换

不能把产品写死在 GPT 6 Luna / Sol / Astra。

## 原则 9：JEV 也可替换

长期设计中 JEV 只是一个 Classifier Provider。

未来允许：

```text
Classifier：
● JEV
○ Local Classifier
○ Other Classifier
```

# 三十八、什么情况下应该暂停继续开发

以下情况出现时，不应继续盲目堆功能：

## 情况 1

JEV 判断与随机/简单规则相比没有明显价值。

## 情况 2

JEV 判断成本吃掉了大部分节省。

## 情况 3

Router 经常把困难任务分给弱模型，导致大量返工。

## 情况 4

总体成本没有下降。

## 情况 5

产品需要大量人工调整，反而比手动选模型更麻烦。

出现这些情况，应优先调整：

- 分类方式；
- 轻量规则；
- JEV Prompt；
- 路由策略；
- 模型能力标注；

而不是继续增加 UI 或插件数量。

# 三十九、产品最终愿景

如果核心验证成立，JEV Model Router 最终希望成为：

> **一个独立于具体 Agent 和具体模型的通用 AI 模型调度层。**

用户不再需要每天考虑：

```text
这个任务该用 Luna？
还是 Sol？
还是 Astra？
还是 DeepSeek？
```

用户只需要选择：

```text
自动选择
```

Router 负责：

```text
理解任务
↓
判断需要什么能力
↓
比较可用模型
↓
控制预算
↓
选择模型
↓
失败时 fallback
↓
告诉用户为什么这样选
```

但系统永远保留：

**人工接管权。**

---

# 四十、v0.2 最终原则

JEV Model Router 的价值不在于“替用户选择最强模型”。

真正价值是：

> **让不懂模型、不懂开发的普通用户，也能在多个模型之间做出接近合理的成本/能力选择。**

整个项目第一阶段只有一个必须证明的结论：

> **在真实任务里，JEV + Router 的总成本确实低于简单固定模型策略，同时任务质量没有明显变差。**

只有这个结论被真实数据支持，才值得继续增加高级功能。

| 项目 | 决策 |
