## 0. v0.3 冻结版说明

v0.3 保留 v0.2 的产品定位和核心架构，但进一步缩小验证范围，并把 Pilot、成本核算、轻量规则边界和阶段路线写清楚。

本版主要变化：

1. 第一轮不再做 50～100 个任务 Benchmark，改为 **10 个真实任务 Pilot**。
2. 10 个任务只用于 **Go / Adjust / Stop** 可行性判断，不用于宣称具有统计学意义的精确成功率。
3. 难度统计先用 **Low / Medium / High 三档**；JEV 内部仍保留 1～10 原始分数。
4. 阶段 1 只做 **Router Core + CLI / Benchmark Harness**，不做 UI，也不做任何 Agent Adapter。
5. CLI 验证通过只证明 Router Core 决策链可行，**不等于真实 Agent 集成已经验证成功**。
6. 10 个任务中专门保留 1 个 **故障注入任务**，验证 fallback、备用链和成本上限。
7. 每个任务必须固定初始快照、环境和验收标准，避免不同方案互相污染。
8. 10 次 JEV 的 task_type / difficulty 全部做快速人工合理性抽查。
9. 需要人工判断的架构分析、Review 等任务，必须预先定义简单评分清单。
10. 只有预先定义的冲突、边界或关键结论任务才允许额外重复 2～3 次，避免选择性重跑。
11. 正式区分 **生产运行成本** 与 **实验验证成本**。
12. Lightweight Rule Engine 增加白名单、高置信度、小跨度降级、失败标记与抽样审计。
13. v0.3 作为产品定义冻结版。除非技术验证推翻核心假设或产品方向明确变化，否则下一步直接进入《技术验证方案 v0.1》。

# 一、产品一句话定位

**JEV Model Router 是一个面向“不懂技术、主要依靠 Agent 做开发”的个人用户的 AI 模型智能路由工具：在真正调用执行模型之前，通过轻量规则和 JEV 判断任务类型与难度，再结合模型能力和成本自动选择合适模型，在任务质量不明显下降的前提下降低 AI 调用总成本。**

第一阶段首先服务自己。

当实际使用证明有效后，再开源到 GitHub，让其他人使用、测试和完善。

---

# 二、为什么要做这个产品

## 2.1 当前问题

使用 Codex、DeepSeek Harness、PI Agent 等 Agent 做开发时，经常会同时拥有多个不同能力和价格的模型。

例如：

- 一个便宜、速度快、能力较弱的模型；
- 一个中档模型；
- 一个价格较高、能力更强的模型。

真正的问题不是“有没有模型”，而是：

> **普通用户不知道当前任务到底需要哪个级别的模型。**

如果所有任务都使用最强模型：

- 成本很高；
- 很多简单任务浪费高级模型额度；
- 用户需要不断手动判断和切换模型。

如果为了省钱总使用便宜模型：

- 复杂任务可能失败；
- 容易返工；
- 最终总体成本反而更高。

对于不会开发的用户，这个问题更明显，因为用户甚至无法准确判断：

- 这个任务到底难不难；
- 当前是代码修改、架构设计还是调试；
- 是否需要高推理模型；
- 失败究竟是模型不够强，还是任务本身有问题。

因此希望由 Router 帮用户完成这个判断。

# 三、目标用户

## 3.1 第一目标用户

第一目标用户不是专业程序员，而是：

**不懂开发或开发能力较弱，但依赖 AI Agent 完成开发工作的个人开发者、创业者和 AI 工具重度用户。**

典型特征：

- 使用 Codex、DeepSeek Harness、PI Agent 等 Agent；
- 自己不会或不擅长写代码；
- 连开发任务拆解也经常依赖 Agent；
- 同时拥有多个模型或多个模型套餐；
- 不知道什么时候应该使用便宜模型、什么时候需要强模型；
- 希望控制调用成本，但不希望因为省钱导致任务质量明显下降。

## 3.2 第二目标用户

未来开源后，也允许有开发能力的用户使用。

这部分用户可能更关心：

- YAML / JSON 配置；
- 自定义 Router 策略；
- 自定义 Provider；
- 自定义模型能力标签；
- 自定义 Adapter；
- 二次开发。

但这不是 v0.1 / v0.2 MVP 的首要设计对象。

# 四、产品目标

JEV Model Router 的目标不是“永远选择最强模型”。

也不是“永远选择最便宜模型”。

核心目标是：

> **先保证任务有较高概率完成，再在满足能力要求的候选模型中尽可能降低总成本。**

三个核心判断因素确定为：

1. **任务类型**
2. **任务难度**
3. **成本**

“速度”暂时不作为一级路由因素。

以后如果实测发现速度非常重要，可以再增加。

---

# 五、非目标

第一阶段明确不做以下事情：

1. 不做商业化收费系统。
2. 不做用户增长、账号体系、运营后台。
3. 不同时支持十几个 Agent 平台。
4. 不一开始就做复杂的自动学习系统。
5. 不允许 Router 未经用户批准自动修改正式生产路由规则。
6. 不要求普通用户学习 YAML、JSON、环境变量等开发知识。
7. 不追求“一次开发完成所有高级功能”。

第一阶段只证明一件事：

> **JEV + Router 这套机制，是否真的能在保持任务质量的情况下省钱。**

# 六、产品最重要的两个假设

整个项目是否值得继续，取决于两个核心假设。

## 6.1 假设一：JEV 能够稳定判断任务

JEV 至少需要对以下信息给出足够稳定的判断：

- 任务类型；
- 难度；
- 所需能力级别；
- 判断置信度。

如果 JEV 经常把：

```text
简单任务 → 判断成困难任务
```

则 Router 会过度调用高级模型，成本无法降低。

如果 JEV 经常把：

```text
困难任务 → 判断成简单任务
```

则任务失败和返工会增加。

因此：

**JEV 判断准确性不是一个附加指标，而是整个产品成立的前提。**

## 6.2 假设二：路由产生的节省必须大于路由自身成本

Router 不是免费的。

每一次：

```text
任务 → JEV → Router → 执行模型
```

都可能增加：

- JEV Token 成本；
- 网络请求成本；
- 时间成本；
- 失败重试成本。

因此不能只计算最终执行模型费用。

生产环境必须计算：

```text
生产运行成本
=
轻量判断成本
+ JEV 判断成本
+ Router 额外调用成本
+ 执行模型成本
+ fallback 成本
+ 返工成本
+ 正式使用中持续存在的人工纠正成本
```

实验阶段另外单独记录：

```text
实验验证成本
=
Pilot / Benchmark 调用费用
+ 测试夹具搭建时间
+ 人工抽查与人工评审时间
+ 重复运行费用
```

两类成本不能混在一起。一次性的研发验证时间不能污染单次生产路由成本；但如果正式使用后仍需要用户频繁纠正路由、重新选模型或反复验收，这属于真实的产品摩擦成本。

只有生产运行成本真正下降，且产品摩擦没有明显增加，产品才算成功。

# 七、产品成功标准

不再使用“感觉省钱了”作为唯一判断标准。

正式成功标准最终应建立在持续积累的真实任务数据上。早期先用 **10 个真实任务 Pilot** 做可行性闸门；Pilot 通过后，真实使用中的第 11、12、13……个任务继续自然积累，后续再根据 30、50、100 个以上真实数据点逐步细化策略。

## 7.1 最低验证指标

测试中至少记录：

- 总任务数；
- 每个任务类型；
- JEV 判断结果；
- Router 选择模型；
- 执行成功/失败；
- 是否返工；
- 最终总成本；
- JEV / Router 额外成本；
- 与固定模型策略相比的成本变化；
- 与固定模型策略相比的成功率变化。

## 7.2 成功原则

满足：

> **总模型成本明显下降，任务成功率没有明显下降，返工率没有明显上升。**

具体“下降多少百分比算成功”暂时不拍脑袋设定。

先完成第一轮基准测试，再确定正式目标，例如：

```text
总成本下降 ≥ X%
任务成功率下降 ≤ Y%
返工率增加 ≤ Z%
```

X、Y、Z 由真实测试数据决定。

# 八、总体工作流程

第一阶段工作流程：

```text
用户提交任务
        ↓
是否手动指定模型？
   ┌────┴────┐
   是        否
   ↓          ↓
指定模型    轻量规则判断
               ↓
        能否非常明确判断？
          ┌────┴────┐
          是        否
          ↓          ↓
       Router      JEV
                     ↓
              结构化判断结果
                     ↓
                  Router
                     ↓
          任务类型 + 难度
                     ↓
            候选模型集合
                     ↓
               成本策略
                     ↓
            主模型 / 备用模型
                     ↓
                 执行任务
                     ↓
              记录实际结果
```

MVP 到这里结束。

第一阶段不要求 Router 自动学习和修改策略。

# 九、为什么必须有“轻量规则层”

不能让所有任务都调用 JEV。

例如：

- 改一个文件名；
- 读取一个文件；
- 修改一行文字；
- 翻译一句短文本；
- 执行明确的机械操作。

这些任务如果每一次都先调用 JEV：

```text
原始任务成本：1

加入 JEV：
JEV 判断：0.2
执行模型：1

总成本：1.2
```

Router 反而增加成本。

因此采用两级机制：

## 第一层：轻量规则

只识别非常确定的低风险场景。

原则：

> **宁可少拦截，也不要错误判断复杂任务。**

第一版对轻量规则增加四个硬约束：

1. **白名单式规则**：只允许明确列出的简单、低风险操作直接命中。
2. **高置信度才生效**：出现上下文依赖、多文件影响、模糊目标、未知副作用等复杂迹象时，立即交给 JEV。
3. **只允许小跨度降级**：可以从中档降到低成本模型，但不能一次跨多个能力级别把潜在高难任务直接交给最弱模型。
4. **所有绕过 JEV 的规则都留痕**：记录 rule_id、route_source、结果与失败原因，并定期抽样审计。

示例：

```text
route_source: light_rule
rule_id: simple_file_read
```

如果命中轻量规则后任务失败，或后续需要明显更高能力模型才能完成，额外记录：

```text
possible_rule_misclassification
```

某条规则若长期失败率或升级率异常，应优先收紧或删除，而不是继续扩大白名单。

## 第二层：JEV

只有轻量规则无法明确判断时，才调用 JEV。

这样 JEV 负责真正需要语义理解的任务，而不是成为所有请求的固定税费。

# 十、JEV 的职责

JEV 的职责不是决定最终模型名称。

JEV 只负责对任务进行结构化理解。

示例输出：

```json
{
  "task_type": "coding",
  "difficulty": 7,
  "required_capability": "high",
  "cost_sensitivity": "medium",
  "context_size": "medium",
  "confidence": 0.91
}
```

其中至少包含：

- task_type
- difficulty
- required_capability
- confidence

可选字段：

- context_size
- cost_sensitivity
- risk_level
- notes

---

# 十一、为什么 JEV 不直接输出模型名

不设计成：

```text
JEV → GPT 6 Sol
```

而设计成：

```text
JEV
↓
任务属性
↓
Router
↓
模型
```

原因：

模型会不断变化。

以后可能：

- 模型改名；
- 模型价格改变；
- 某模型取消；
- 新增 DeepSeek；
- 新增 Claude；
- 新增 Qwen；
- 新增本地模型。

如果 JEV 直接输出模型名，每次模型变化都可能需要调整分类提示词。

正确做法是：

> **JEV 负责理解任务，Router 负责理解模型。**

---

# 十二、Router 的模型选择逻辑

Router 采用三个主因素：

## 12.1 任务类型

例如：

```text
coding
debugging
architecture
research
writing
translation
review
testing
reasoning
data-analysis
```

任务类型首先用于排除明显不适合的模型。

## 12.2 难度

JEV 内部继续输出 1～10 原始难度分数，便于以后积累更细数据。

但 Pilot 和早期统计只使用三个粗粒度档位：

```text
Low     低
Medium  中
High    高
```

初始只有 10 个任务，如果同时按大量任务类型 × 1～10 难度切格子，每个格子的样本太少，容易产生没有意义的精确数字。

原始 1～10 分保留在日志里，等真实使用数据积累后再决定是否细化阈值。

难度本身不直接绑定模型名称。


## 12.3 成本

在满足能力要求的候选模型中，再比较成本。

原则：

> **先满足能力要求，再在满足条件的模型里选更便宜的。**

不是：

> 最便宜模型永远优先。

---

# 十三、模型配置

每个模型至少记录：

```text
模型名称
Provider
能力等级
擅长任务类型
不适合任务类型
输入价格
输出价格
上下文能力
当前是否可用
凭证引用
```

未来可以增加：

- 成功率；
- 平均返工率；
- 平均响应时间；
- 实测 Coding 能力；
- 实测 Review 能力。

这些数据不要求第一版全部自动生成。

---

# 十四、主模型、备用模型和成本上限

每类任务可以配置：

```text
主模型
备用模型 1
备用模型 2
单任务成本上限
```

例如：

```text
任务类型：普通 Coding

主模型：
GPT 6 Sol

备用：
DeepSeek
GPT 6 Astra

单任务最大预算：
$0.50
```

当主模型：

- 不可用；
- 超时；
- 额度不足；
- 调用失败；

才进入备用链。

不能无限升级。

超过预算上限后停止自动升级，并向用户说明原因。

---

# 十五、JEV 故障降级

JEV 不能成为系统单点故障。

基本降级流程：

```text
JEV 正常
→ 正常路由

JEV 超时 / 报错
→ 使用保守规则判断

仍无法判断
→ 使用默认保底模型

保底模型失败
→ 进入备用模型链
```

同时记录：

```text
fallback_reason
```

例如：

```text
fallback_reason: jev_timeout
```

---

# 十六、手动选择模型

Router 必须保留人工控制权。

UI 的模型选择控件默认：

```text
● 自动选择
○ GPT 6 Luna
○ GPT 6 Sol
○ GPT 6 Astra
○ DeepSeek
○ Claude
○ 其他模型
```

默认是：

**自动选择**

代表：

```text
轻量规则 → JEV（必要时）→ Router
```

如果用户手动选择：

```text
GPT 6 Astra
```

此次任务直接使用该模型。

记录：

```text
route_source: manual_override
```

手动选择只覆盖当前任务。

不能偷偷修改全局默认规则。

下一次新任务默认仍回到“自动选择”。

---

# 十七、UI 是普通用户的主路径

v0.2 明确调整优先级：

**UI 是唯一必须打磨好的普通用户路径。**

普通用户不应该需要理解：

- YAML；
- JSON；
- Provider 配置格式；
- 环境变量；
- 终端命令；
- Router 内部算法。

普通用户应该可以通过 UI 完成：

- 添加模型；
- 选择 Provider；
- 设置 API 凭证；
- 设置模型价格；
- 设置模型能力等级；
- 设置主模型；
- 设置备用模型；
- 设置预算上限；
- 开启自动路由；
- 手动选择模型；
- 查看 Router 为什么选择这个模型；
- 查看本次大概花费；
- 查看 fallback 是否发生。

---

# 十八、开发者配置路径

配置文件仍然保留，但降为高级能力。

例如：

```text
models.yaml
router.yaml
providers.yaml
privacy.yaml
```

原则：

> 普通用户完全不碰配置文件，也能够正常使用全部核心功能。

开发者可以直接修改配置文件，以便：

- 批量配置；
- 自动部署；
- Git 管理；
- 二次开发；
- 自定义 Provider。

MVP 可以先实现内部配置存储，但不要求第一阶段把“手动编辑 YAML”打磨成完整产品功能。

# 十九、UI 首页建议

UI 第一原则：

**普通人打开后能够马上知道现在是什么状态。**

示例：

```text
JEV Model Router

Router：运行中
JEV：正常
模式：Local

模型选择：
[ 自动选择 ▼ ]

当前策略：
任务类型 + 难度 + 成本

最近一次路由：

任务类型：Coding
难度：6
最终模型：GPT 6 Sol
选择原因：
Luna 能力不足
Astra 成本更高

本次总成本：
$0.0xx

其中：
JEV 判断成本：$0.00x
执行模型成本：$0.0xx
```

关键要求：

用户必须能看懂：

> **为什么这次选择了这个模型，以及这次到底花了多少钱。**

# 二十、凭证管理

Router 不直接在普通配置文件中保存明文 API Key。

配置中保存：

```text
credential_ref: openai-main
```

底层根据部署环境读取：

- macOS Keychain；
- 环境变量；
- Docker Secret；
- Server Secret Manager；
- 后续其他凭证系统。

UI 对普通用户可以显示：

```text
OpenAI：已连接
JEV：已连接
DeepSeek：未配置
```

而不是直接展示完整密钥。

# 二十八、10 个真实任务 Pilot

正式扩展功能之前，先做一轮成本可控的可行性验证。

## 28.1 Pilot 目的

第一轮只跑 **10 个真实任务**。

这 10 个任务不是为了得出具有统计学意义的精确成功率，只用于做产品闸门判断：

```text
Go      → 没有明显致命问题，值得继续
Adjust  → 有价值，但 JEV / Router / 规则需要调整
Stop    → 核心假设没有得到初步支持，暂停扩功能
```

Pilot 通过后，不再为了凑样本提前烧费用。后续真实使用中的任务自动成为新的数据点，逐步积累到 30、50、100 个以上再做更稳定分析。

## 28.2 任务组成

10 个任务必须来自真实开发工作，建议覆盖：

- 2 个 Low：机械操作或小型修改；
- 4 个 Medium：普通 Coding / Debug / Testing；
- 2 个 Medium~High：较复杂 Review / Debug / 多文件任务；
- 1 个 High：架构、复杂推理或长上下文任务；
- 1 个 **故障注入任务**：专门验证 fallback、备用模型链和成本上限。

## 28.3 故障注入任务

该任务不测试模型能力，而是确认：主模型不可用时是否进入备用模型、fallback_reason 是否正确、备用链是否按顺序执行、成本上限能否拦停无限升级、最终错误是否清楚。

优先使用 mock failure、无效测试模型或专门测试配置等受控方式，不破坏正式账号、正式密钥或生产配置。

## 28.4 每个任务必须固定初始状态

每个 Pilot 任务运行前固定：任务 ID、初始代码/文件快照、仓库 commit（如适用）、Prompt、Router 配置版本、工具权限、上下文材料、模型版本、超时/Token 上限、验收标准和允许修改范围。

任何会修改代码或文件的任务，每次比较前都恢复到同一个起点。

## 28.5 对照方式：控制费用

第一轮不要求每个任务都跑“便宜 / 中档 / 高档 / Router”四套方案。

主要比较：

```text
当前真实 Baseline
vs
JEV Router
```

只有关键任务、Router 失败、边界判断或需要确认模型能力差异时，才补跑相邻能力模型。

## 28.6 验收标准必须预先固定

Coding / Debug / Testing 优先自动验收：指定测试通过、回归测试无新增失败、不修改禁止范围、必要的 build/lint/typecheck 通过、目标功能存在。

不能看到结果后再改变“成功”的定义。

## 28.7 人工任务使用固定评分清单

架构分析、Review、方案设计等任务，执行前定义 3～5 条勾选项，至少考虑：是否覆盖主要约束、是否存在明显错误、是否遗漏改变结论的重要风险、是否支持下一步行动、是否出现无依据重大结论。

每项任务提前声明哪些勾选项属于必须通过。

## 28.8 JEV 判断单独人工抽查

10 个任务的 JEV 输出全部保留并快速检查：task_type 是否明显不合理、Low/Medium/High 是否明显离谱、required_capability 是否基本相符、confidence 是否与确定性大体一致。

记录为：

```text
reasonable
questionable
clearly_unreasonable
```

这里不追求给“难度 6 还是 7”建立绝对真值。真正重要的是两件事：

1. **分类合理性**：JEV 的 task_type / difficulty 是否明显离谱。
2. **决策有效性**：这些判断是否真的帮助 Router 选择了更合适的模型。

## 28.9 模型随机性与重复运行规则

不把某一次成功/失败直接当成模型能力定论，也不把全部任务重复三遍。

只有满足预先定义条件之一，才允许额外重复验证：

1. Router 选择模型未通过验收，但相邻更高能力模型补跑后通过；
2. JEV confidence 低于 Pilot 开始前固定的阈值；
3. JEV 原始难度位于 Low / Medium / High 分档边界附近；
4. 人工评分被标记为 borderline / questionable；
5. 出现与主要结论直接相关的异常失败或非预期 fallback。

触发后最多额外运行 2 次，即最多形成 3 次同起点结果。不能因为结果“不符合预期”就临时决定重跑。

## 28.10 记录指标

每项任务至少记录：任务 ID、任务类型、JEV 原始难度、难度档、JEV 判断与置信度、JEV 人工合理性检查、Router 选择、route_source、rule_id（如适用）、最终模型、JEV 成本、执行成本、fallback 成本、生产运行总成本、成功/失败、返工次数、是否触发重复验证、最终是否完成。

实验阶段另外单独记录测试夹具搭建时间、人工评审时间、重复验证费用等实验验证成本。

## 28.11 Pilot 最终只回答四个问题

1. Router 链路能不能稳定跑通？
2. Router 相比当前 Baseline 有没有初步省钱迹象？
3. 省钱后任务质量有没有明显恶化？
4. JEV 判断和路由自身的额外成本是否值得？

最终只输出：**Go / Adjust / Stop**。

如果不理想，优先调整 JEV Prompt、轻量规则、模型能力标注和 Router 策略，而不是继续增加 UI、Adapter 或高级功能。

# 三十五、设计原则

## 原则 1：普通用户优先

不假设用户懂开发。

## 原则 2：先证明省钱

不要因为产品听起来聪明，就默认它有价值。

## 原则 3：总成本，而不是单次模型价格

JEV 自身成本必须计入。

## 原则 4：不牺牲明显质量换成本

失败和返工也是成本。

## 原则 5：路由可解释

至少告诉用户：

```text

```

## 原则 6：最终控制权属于用户

自动模式是默认。

手动覆盖始终存在。

## 原则 7：核心与平台解耦

Router Core 不绑定 Codex、DeepSeek Harness 或 PI Agent。

## 原则 8：模型可替换

不能把产品写死在 GPT 6 Luna / Sol / Astra。

## 原则 9：JEV 也可替换

长期设计中 JEV 只是一个 Classifier Provider。

未来允许：

```text
Classifier：
● JEV
○ Local Classifier
○ Other Classifier
```

# 三十八、什么情况下应该暂停继续开发

以下情况出现时，不应继续盲目堆功能：

## 情况 1

JEV 判断与随机/简单规则相比没有明显价值。

## 情况 2

JEV 判断成本吃掉了大部分节省。

## 情况 3

Router 经常把困难任务分给弱模型，导致大量返工。

## 情况 4

总体成本没有下降。

## 情况 5

产品需要大量人工调整，反而比手动选模型更麻烦。

出现这些情况，应优先调整：

- 分类方式；
- 轻量规则；
- JEV Prompt；
- 路由策略；
- 模型能力标注；

而不是继续增加 UI 或插件数量。

```text
比较可用模型
↓
控制预算
↓
选择模型
↓
失败时 fallback
↓
告诉用户为什么这样选
```

但系统永远保留：

**人工接管权。**

# 四十、v0.3 冻结版最终原则

JEV Model Router 的价值不在于“替用户选择最强模型”。

真正价值是：

> **让不懂模型、不懂开发的普通用户，也能在多个模型之间做出接近合理的成本/能力选择。**

整个项目第一阶段只有一个必须证明的结论：

> **在真实任务里，JEV + Router 的总成本确实低于简单固定模型策略，同时任务质量没有明显变差。**

只有这个结论被真实数据支持，才值得继续增加高级功能。

## 附：v0.3 冻结版当前已经确定的产品决策

冻结规则：

> 从 v0.3 起，产品定义阶段结束。后续默认进入技术验证文档，不再因为实现细节持续扩写产品方案。只有技术验证推翻核心假设、真实 Agent 集成暴露产品级问题，或用户明确改变产品方向时，才重新开启产品定义版本。

| 项目 | 决策 |
|---|---|
| 核心判断因素 | 难度 + 成本 + 任务类型 |
| JEV 输出 | 结构化判断，不直接输出模型名 |
| 配置策略 | 中心配置 + 平台覆盖 |
| 判断方式 | 轻量规则 + JEV 两级路由 |
| 模型失败策略 | 主模型 + 备用模型 + 成本上限 |
| 路由优化 | 未来记录结果并生成建议，用户批准后生效 |
| 产品形态 | Router Core + API + 平台 Adapter |
| 部署 | Local / Server 均支持 |
| JEV 失败 | 分级 fallback |
| 凭证 | 统一凭证管理层 |
| UI / 配置 | UI 为普通用户主路径，配置文件为高级路径 |
| 长任务 | 架构兼容分层路由，Pilot 与首轮集成均不要求完整实现 |
| 隐私 | 分级隐私模式 |
| 手动模型 | 默认自动；用户可临时手动覆盖 |
| 商业化 | 第一阶段不考虑 |
| 开源 | 自用验证成功后考虑 GitHub 开源 |
| Pilot 规模 | 初始 10 个真实任务，之后依靠真实使用持续积累 |
| 难度统计 | Pilot 使用 Low / Medium / High，保留 1～10 原始分 |
| 阶段 1 | 只做 Core + CLI / Benchmark Harness，不做 UI / Adapter |
| 核心成功指标 | 生产运行成本下降且任务质量不明显下降 |
